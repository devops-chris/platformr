# Changing existing resources

Most day-2 work is a small change to something that already exists: scale a
service, upgrade a cluster, allow an IP, add a permission, add a user. A **change
request** does that. The developer picks the thing, sees its current settings,
picks new ones, and gets a PR that changes exactly those values.

```
$ platformr request
? What type of resource?          › EKS
? What would you like to request? › Upgrade cluster version
? Which cluster?                  › apps
? Kubernetes version (now: 1.32)  › 1.33

This request changes:
  Kubernetes version: 1.32 → 1.33

? Open a pull request with this change? Yes
✓ PR opened
```

Four complete, tested examples (Helm, Terraform, a security group, an IAM policy)
are in [`examples/changeable/`](https://github.com/devops-chris/platformr/tree/main/examples/changeable/). The settings themselves
are listed in [configuration.md](configuration.md#change-requests-editing-existing-files).

---

## How it works

A change request names **a file** and **where in it**:

```toml
[[resources]]
name         = "eks-upgrade"
category     = "EKS"
display_name = "Upgrade cluster version"
update_file  = 'clusters/{{.name}}/main.tf'        # which file

  [[resources.fields]]
  name    = "cluster_version"
  type    = "select"
  label   = "Kubernetes version"
  options = ["1.33", "1.34"]
  key     = "module.eks.cluster_version"           # where in it
```

When the developer runs it, platformr:

1. **Reads the file** from the repo's main branch.
2. **Starts each question on the current value** at its `key`, shown as
   "(now: 1.32)". The current value is always pickable, even if it's not on the
   approved list.
3. **Writes the answers back** to the same spots, plus any list or map changes
   from `[[resources.changes]]`.
4. **Shows the summary** (`1.32 → 1.33`) and asks to confirm.
5. **Opens a PR** with the changed file.

**Only the changed values are touched.** platformr finds each value's exact position
in the file and replaces just that text. Comments, ordering, quoting and indentation
stay as they were, so the PR diff shows only what the developer changed.

**It doesn't matter who wrote the file.** It can be hand-written, generated by
platformr, or anything else. platformr reads it fresh every time.

**Values keep their type.** A number stays a number and quoted text stays quoted. If
`cpu: 500m` becomes `1`, it's written as `"1"` so it's still text.

## Who knows what

platformr doesn't know about Helm, Terraform, IAM or any tool. It knows a few
**file formats** and how to find a spot in them. Everything about *your*
infrastructure (which files, which keys, which choices are allowed) is in your
`platformr.toml`, written by your platform team.

| Part | Where it lives | Who changes it |
|---|---|---|
| Which requests exist ("EKS › Upgrade cluster version") | `platformr.toml` | platform team |
| Which file, which key, the allowed choices | `platformr.toml` | platform team |
| Reading and editing YAML, JSON, HCL, ... | platformr | platformr release |

A new tool, a new action, or a new approved version is a config change. platformr
itself only needs an update for a new file format or a new kind of change.

### How platformr knows the format

From the file extension:

| Extension | Format |
|---|---|
| `.yaml`, `.yml` | YAML |
| `.json`, `.tf.json`, `.tfvars.json` | JSON |
| `.tf`, `.tfvars`, `.hcl`, `.nomad` (incl. `terragrunt.hcl`) | HCL |
| `.env`, `.env.*`, `.properties`, `.ini` | key=value |

Anything else needs `format = "yaml"` (or `json`, `hcl`, `env`, `marker`) on the
request. If platformr can't tell, it says so before asking any questions, and
`platformr doctor` reports it too.

## Pointing at a value: keys

| You write | It means |
|---|---|
| `key = "replicaCount"` | top-level `replicaCount` |
| `key = "resources.requests.cpu"` | nested: `resources` → `requests` → `cpu` |
| `key = "module.eks.cluster_version"` | HCL: `cluster_version` in `module "eks" { }` |
| `key = "locals.cluster_version"` | HCL: in the `locals { }` block |
| `key = ["config", "myproject:nodeCount"]` | list form: each part kept whole, for names containing `.` or `:` (Pulumi) |
| `key = ["Statement", { Sid = "S3Read" }, "Action"]` | `{ field = value }` picks the one list item that matches |
| `key = ["users", 0, "name"]` | a number picks a list position |
| `key = "marker:node_count"` | the line tagged with a `platformr:node_count` comment (see [Line markers](#line-markers-for-any-other-file)) |

Any part can use earlier answers: `{ Sid = "{{.sid}}" }`.

In HCL, blocks with the same type and no name (several `statement { }` blocks) are
picked the same way: `["data", "aws_iam_policy_document", "ci", "statement", { sid = "Logs" }, "actions"]`.

## Changing values

Put a `key` on a question. It starts on the current value and writes the answer
back. A request can have as many as it needs, in one PR:

```toml
  [[resources.fields]]
  name    = "replicas"
  type    = "select"
  options = ["1", "2", "3", "4", "6"]
  key     = "replicaCount"

  [[resources.fields]]
  name    = "cpu"
  type    = "select"
  options = ["250m", "500m", "1"]
  key     = "resources.requests.cpu"
```

- **A question can point at a different file** with its own `update_file`, so one
  request can change values in several files.
- **A `computed` question with a `key`** writes a derived value. For example, one
  "Size: small / medium / large" pick can set CPU and memory together through a
  `[maps]` lookup.
- **Picking the value that's already there** isn't a change. If nothing changed, no
  PR is opened.

## Lists and maps: adding and removing

`[[resources.changes]]` entries add or remove items. They run in order, after the
questions.

| `action` | What it does | Also needs |
|---|---|---|
| `append` | add an item to a list | `key`, `item` |
| `remove` | take matching items out of a list | `key`, `match` |
| `put` | add a named entry to a map | `key`, `name`, `item` |
| `delete` | remove a named entry from a map | `key`, `name` |
| `set` | change one value (like a question's `key`, without asking) | `key`, `value` |
| `delete_file` | delete a whole file | `file` |

An **item** is a plain value or an object:

```toml
item = "{{.cidr}}"
item = { name = "{{.username}}", role = "{{.role}}" }
```

New objects follow the field order and types of the items already in the list.

A **match** is a plain value or the fields an object must have:

```toml
match = "{{.cidr}}"
match = { name = "{{.username}}" }
```

**`unique_by`** stops an `append` when the item is already there:
`unique_by = "value"` for plain lists, or a field name (`"name"`) for objects. Add
`if_exists = "skip"` to carry on without adding it instead.

**Creating and changing together.** A request can also render templates
(`template`, `template_dir` or `template_files`) and make changes in the same PR,
for example a new account's folder plus its entry in the organization's account
list. Nobody has to make two requests that must agree with each other.

**Pickers for "remove" requests.** `list` on a question fills it with what's in the
file now, so the developer can only pick something that exists:

```toml
  [[resources.fields]]
  name = "username"
  type = "select"
  list = "users"
  show = "name"      # users are objects; list them by name. Not needed for plain values or map names.
```

Add `allow_manual = true` to also offer "[+ enter manually]", for a value that isn't
in the list yet.

**`when`** on a change skips it unless the expression is true, the same as on a
question.

### One list in a file, or one file per item?

Both work. Pick per collection:

| | One list in a file | One file per item |
|---|---|---|
| Add | `append` / `put` | a normal create request (a new file) |
| Remove | `remove` / `delete` | `delete_file` |
| Two people adding at once | the second PR has a merge conflict | both merge cleanly |
| Good for | small, rarely changed lists: CIDRs, policy actions | busy collections: users, DNS records, accounts |

For one file per item, the IaC reads the whole folder: `fileset()` in Terraform, one
Crossplane claim per item, or a loop in Pulumi/CDK.

## Safety checks

- **The config is checked before any question is asked.** That covers a missing file,
  an unknown format, or a change without what its action needs. `platformr doctor`
  runs the same check for every request.
- **The file must exist.** If the picked file isn't in the repo, the request stops
  and says so.
- **One open change per file.** If a platformr PR changing the same file is already
  open, the request stops and links to it. A second change would start from
  out-of-date values.
- **Ambiguous keys stop the request.** If a `{ field = value }` match finds no items
  or several, or a name isn't there, platformr explains which part of the key
  failed instead of guessing.

## What platformr can and can't change

| Format | Works | Doesn't |
|---|---|---|
| **YAML** | values, nested values, lists and maps (block or `[...]`/`{...}` style) | multi-line text (`|` / `>`), values with an explicit `!!tag` |
| **JSON** | everything | |
| **HCL** | values written out in the file, lists and maps, inside `toset()` / `tolist()` / `tomap()` / `jsonencode()` | anything computed: `var.x`, `local.y`, `merge(...)`, `format(...)`. platformr says "can't change it" instead of guessing |
| **key=value** | values, including under `[section]` headers (`section.key`) | lists (these files don't have them) |
| **line markers** | one value per marked line | lists |
| **TOML** | not yet | |

**HCL formatting:** if the file was already `terraform fmt`-formatted, it's
re-formatted after the change, so `=` signs stay aligned. A longer new key can then
re-align its neighbors, and the diff shows those as whitespace changes. If the file
wasn't formatted, it's left alone.

### Line markers, for any other file

For a format platformr doesn't read (TypeScript, Python, Go, Bicep, Jsonnet, CUE),
put a comment on the line holding the value:

```ts
const cluster = new eks.Cluster(this, "apps", {
  version: "1.32", // platformr:cluster_version
  nodeCount: 3,    // platformr:node_count
});
```

```toml
key = "marker:cluster_version"
```

platformr changes the last string, number or `true`/`false` before the marker, and
keeps its quotes. Each marker must be unique in the file.

## Notes by tool

**Helm (Argo CD / Flux).** Change values in the service's own `values.yaml`, or in a
separate values file listed last in Argo CD's `valueFiles` if you want to keep
platformr's changes apart from hand edits. If the values are written inline in the
Argo CD Application (`helm.values`), there's no file to point at; move them to a
values file first.

**Terraform / OpenTofu / Terragrunt.** Point keys at plain values: `locals { }`,
`module "x" { }` arguments, `*.tfvars`, or Terragrunt `inputs`. Keep values that
change often written out, not computed.

**Crossplane / Kubernetes.** The claim or manifest is YAML; point keys into `spec`.

**Pulumi.** Per-stack settings live in `Pulumi.<stack>.yaml` under `config:`, with
names like `myproject:nodeCount`. Use the list form:
`key = ["config", "myproject:nodeCount"]`. platformr only changes that value, so
encrypted secrets in the file are untouched.

**AWS CDK / CDKTF.** Settings usually live in `cdk.json` (`context`) or a JSON/YAML
config file the app reads. For values written directly in code, use line markers.
